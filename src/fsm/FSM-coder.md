# FSM Code Generator Constitution（完整版）

本宪法是 FSM 代码生成器的最高设计准则。所有模块、数据结构、算法和 CLI 行为必须遵守本宪法；如需偏离，必须在本文件末尾新增修正案并说明理由。

---

## 第一条：IR 结构定义

整个系统的唯一事实来源是 **FsmIR**。

- FsmIR 由 EventDef、StateDef、TransitionDef 组成，所有行为必须由 IR 数据驱动。
- 禁止在代码生成器中硬编码任何状态名、事件名、转移规则。
- 禁止通过环境变量、全局变量、隐式上下文传递 FSM 定义。
- IR 必须支持版本字段，便于后续前向/后向兼容。

---

## 第二条：不变量验证器

代码生成前必须通过全部不变量检查。

- 验证器必须覆盖以下检查项：
  - from / goto 必须引用已定义状态
  - on 必须引用已定义事件
  - 有且仅有一个初始状态
  - nestable 状态必须声明 exit_event
  - exit_event 必须引用已定义事件
  - 同一 (from, on) 不允许重复定义
  - 初始状态不可作为 goto 目标
  - 不可达状态必须报告 Warning
- 验证器必须**收集全部违规项后一次性报告**，禁止 fail-fast 只报第一个。
- 验证器必须是纯函数，不得修改 IR。

---

## 第三条：数据持有规范

状态机运行时数据必须与转移逻辑分离。

- State 持有自身数据（如栈、缓冲区、上下文）。
- Action 必须是纯函数，输入为当前数据 + 事件，输出为新数据。
- 禁止全局可变状态。
- 禁止在 Action 中执行 I/O、网络请求、文件系统操作。
- 所有副作用必须通过返回值显式传递。

---

## 第四条：代码生成器

生成器将 FsmIR 转换为目标语言源码。

- 生成的代码必须包含头部注释，标明来源 IR 和生成时间。
- 生成的 match 分支必须与 IR 中 transitions 的顺序一致。
- 禁止生成压缩代码、混淆变量名、省略换行。
- 生成的代码必须是**可编译的**，不得包含语法错误或未解析的占位符。
- 生成器必须是纯函数，相同 IR + 相同配置必须产出相同代码。

---

## 第二条细则：不变量验证器实施细则

### 2.1 诊断信息结构

所有诊断信息必须使用统一结构：

```
Diag {
  rule: String,              // 规则编号，如 "INV-1"
  severity: Severity,        // Error | Warning
  message: String,           // 人类可读描述
  location: Option[SourceLocation],  // 文件名 + 行号 + 列号
  suggestion: Option[String],        // 修复建议（可选）
}
```

### 2.2 规则清单

| 编号 | 规则 | 严重度 | 说明 |
|------|------|--------|------|
| INV-1 | from 必须引用已定义状态 | Error | 转移来源不存在 |
| INV-2 | on 必须引用已定义事件 | Error | 触发事件不存在 |
| INV-3 | goto 必须引用已定义状态 | Error | 转移目标不存在 |
| INV-4 | 有且仅有一个初始状态 | Error | 初始状态数量不合法 |
| INV-5 | nestable 状态必须声明 exit_event | Error | 可嵌套状态缺少退出事件 |
| INV-6 | exit_event 必须引用已定义事件 | Error | 退出事件不存在 |
| INV-7 | 同一 (from, on) 不允许重复 | Warning | 转移规则冲突 |
| INV-8 | 不可达状态报告 Warning | Warning | 存在孤立状态 |

### 2.3 错误恢复建议

验证器在报告错误的同时，应尽可能提供修复建议：

- from 引用不存在 → 建议最相似的状态名（编辑距离 ≤ 2）
- on 引用不存在 → 建议最相似的事件名
- 缺少初始状态 → 建议将第一个状态标记为初始
- 重复 (from, on) → 建议合并或删除其中一个

---

## 第三条细则：数据持有规范实施细则

### 3.1 State 数据结构

每个状态必须定义其持有的数据类型：

```
StateData {
  state_id: String,
  fields: Array[FieldDef],  // 字段名 + 类型
}
```

### 3.2 Action 签名

所有 Action 必须遵循统一签名：

```
fn action_name(data: StateData, event: Event) -> Result[StateData, ActionError]
```

- 输入：当前状态数据 + 触发事件
- 输出：新状态数据 或 错误
- 禁止在 Action 中直接修改外部状态

### 3.3 副作用隔离

如需执行 I/O 操作，必须通过以下方式：

- Action 返回 Effect 描述（如 WriteFile(path, content)）
- 由外部运行时解释并执行 Effect
- Action 本身保持纯函数特性

---

## 第四条细则：代码生成器实施细则

### 4.1 生成代码结构

生成的代码必须包含以下部分：

```
// ===== 头部注释 =====
// Generated by fsm-gen from {source_file}
// Generated at {timestamp}
// Do not edit manually.

// ===== 类型定义 =====
// State 枚举、Event 枚举、StateData 结构体

// ===== 转移函数 =====
// fn step(state: State, event: Event, data: StateData) -> StepResult

// ===== Action 分发 =====
// fn dispatch_action(action: String, data: StateData) -> StateData

// ===== Debug 辅助（可选）=====
// fn trace_state(state: State) -> String
```

### 4.2 代码风格

- 缩进：2 空格
- 每行不超过 100 字符
- 变量命名：snake_case
- 类型命名：PascalCase
- 函数命名：snake_case

### 4.3 生成代码编译验证

生成器产出代码后，必须自动调用目标语言的编译器/检查器验证：

```
生成代码 → 写入临时文件 → 调用 moon check → 检查退出码
```

- 编译失败时，输出编译器错误信息并终止
- 编译成功时，删除临时文件

---

## 第五条：测试规范

生成器必须有完整的测试保障。

### 5.1 单元测试

- 每个模块必须有独立的单元测试
- 使用 MoonBit 内置 test 块
- 测试覆盖率目标：核心逻辑 ≥ 80%

### 5.2 快照测试

- 每个 IR 输入对应一个 expected/ 快照文件
- 快照测试覆盖场景：
  - 全量生成
  - 增量生成（无变更）
  - 增量生成（有变更）
  - debug 模式
  - 校验失败
- 快照变更时必须人工确认并更新

### 5.3 端到端测试

- 从 IR 输入 → 验证 → 生成 → 编译 → 运行，全链路自动化
- 测试用例必须包含：
  - 正常路径（合法 IR → 正确代码）
  - 异常路径（非法 IR → 正确错误报告）
  - 边界路径（空 IR、单状态、大量状态）

### 5.4 测试数据管理

```
test/
├── fixtures/
│   ├── valid/          # 合法 IR 文件
│   └── invalid/        # 非法 IR 文件（预期报错）
├── expected/
│   ├── valid/          # 合法 IR 的预期生成代码
│   └── invalid/        # 非法 IR 的预期诊断信息
└── snapshots/          # 快照文件
```

## 第六条：可观测性规范

生成的状态机必须具备可观测能力。

### 6.1 状态转移日志

- debug 模式下，每次转移必须输出日志：

```
[FSM] {pos}: {from_state} --[{event}]--> {to_state}
```

- 日志格式必须统一，便于 grep 和解析
- 日志不得影响状态机语义行为

### 6.2 状态机可视化

- 支持从 FsmIR 生成 DOT/Graphviz 格式
- 输出文件包含：
  - 所有状态节点（初始状态用双圈标记）
  - 所有转移边（标注事件名和 action）
  - 嵌套关系（如有）

```
fsm visualize input.ir -o output.dot
dot -Tpng output.dot -o output.png
```

### 6.3 运行时度量（可选）

- 各状态停留时长
- 转移频率统计
- 异常事件计数

度量数据通过回调函数上报，生成器不直接依赖具体监控系统。

---

## 第七条：可扩展性规范

生成器必须支持扩展和多后端。

### 7.1 插件/钩子机制

生成器在以下节点提供钩子：

- before_generate：生成前预处理 IR
- after_generate：生成后处理代码字符串
- custom_action：用户自定义 Action 实现

钩子通过配置文件注册，不得修改生成器核心逻辑。

### 7.2 多后端生成

生成器架构必须支持多目标语言：

```
FsmIR → Backend Interface → MoonBit Backend
                          → TypeScript Backend
                          → Rust Backend
```

- 每个后端实现统一的 Backend trait
- 后端选择通过 CLI 参数指定：--target moonbit

### 7.3 分层状态机（HSM）

- IR 中 StateDef 预留 parent 字段
- 验证器检查父子关系合法性
- 生成器支持嵌套状态的 enter/exit 逻辑

### 7.4 并发状态机

- 支持正交区域（Orthogonal Regions）
- 多个独立状态维度并行运行
- 每个区域有独立的初始状态

---

## 第八条：工程化基础设施

生成器必须具备工程化能力。

### 8.1 CLI 工具

统一命令行入口：

```
fsm validate input.ir          # 仅校验
fsm generate input.ir -o out.mbt  # 生成代码
fsm visualize input.ir -o out.dot   # 生成可视化
fsm test input.ir              # 运行测试
```

### 8.2 增量生成

- 缓存文件存储 IR 哈希 + 配置哈希 + 状态级代码哈希
- 无变更时跳过写入，保持文件 mtime 不变
- 缓存损坏时自动退化为全量生成

### 8.3 版本兼容性

- IR schema 必须包含 version 字段
- 新版本必须能解析旧版本 IR（后向兼容）
- 废弃字段必须标记 deprecated 并保留至少一个版本

### 8.4 文档生成

- 从 IR 自动生成 Markdown 文档
- 文档包含：
  - 状态说明表
  - 转移规则表
  - 数据流图

修正案 A-001：移除底层张量存储，确立 FsmIR 唯一核心地位
日期：2026-08-17
修改内容：
明确废弃 FsmTensor、CooStorage、CsrStorage 等底层稀疏矩阵存储结构。
确立 FsmIR 为系统中唯一的内存数据结构。
优化算子（prune, minimize, fuse）的签名统一为 fn(FsmIR) -> FsmIR，彻底消除 IR -> Tensor -> IR 的格式转换开销。
理由：FSM 的状态规模通常在几十到几百之间，属于典型的“小规模图论问题”。引入 COO/CSR 等矩阵存储属于过度设计，不仅增加了数百行底层维护代码，还引入了不必要的内存拷贝开销。FsmIR 配合内置的 Map<String, Int> 索引，足以在毫秒级完成所有图遍历与优化操作。
修正案 A-002：算子接口正交化与管线化规范
日期：2026-08-17
修改内容：
在第七条（可扩展性规范）中补充“算子接口规范”。
规定所有图优化算子必须遵循 FsmIR -> FsmIR 的纯函数签名。
支持通过管道操作符（如 |>）进行无缝组合：build() |> validate() |> prune() |> minimize() |> codegen()。
理由：保持接口的高度一致性，避免引入类似 PrunedMatrix、MinimizedMatrix 等语义泄漏的中间类型。统一的输入输出使得优化管线可以像 Unix 管道一样灵活编排，极大提升了可测试性和可观测性。
修正案 A-003：验证器错误恢复与编辑距离建议
日期：2026-08-17
修改内容：
在第二条细则（2.3 错误恢复建议）中，明确“编辑距离（Levenshtein Distance）”算法的实现要求。
当触发 INV-1、INV-2、INV-3（引用不存在）时，验证器必须在 suggestion 字段中返回编辑距离 ≤ 2 的候选项。
理由：在 DSL 或配置文件编写中，拼写错误是最常见的异常。提供精准的修复建议（如：“Did you mean 'Running'? ”）能将开发者的 Debug 时间从分钟级缩短到秒级，显著提升 DX（开发者体验）。
